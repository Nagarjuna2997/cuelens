# Eye-contact correction: integration status

Reviewed November 13, 2026. **CueLens does not currently redirect pupils or head pose.** Its camera framing changes the crop; posture coaching observes visible position. Neither makes an off-camera gaze appear centered. The existing eye-contact status therefore remains **Unavailable**.

An acceptable integration needs a usable camera-processing SDK or an independently installed virtual-camera provider, appropriate model and distribution rights, and observed correction on this Mac. A toggle, face detector, or geometric pixel shift does not establish that capability. The user authorized a separate local GazeAt trial. That evaluation is described below; no gaze model or vendor binary is bundled with CueLens.

## Native SDK and model verification

A read-only search of the installed MacOSX27.2 SDK's public AVFoundation, Vision, and CoreImage headers and Swift interfaces found no eye-contact or gaze-redirection API. AVFoundation's documented Center Stage behavior changes framing, while Portrait, Studio Light, and Background Replacement address other effects. None is an eye-redirection switch for CueLens.

The GazeAt candidate's FLX implementation traces to the original [gaze_correction project](https://github.com/chihfanhsu/gaze_correction), which includes trained weights and a BSD source license. Its original [DIRL dataset](https://sites.google.com/site/chihfanhsuwebsite/dataset) is marked for noncommercial use, and dlib separately flags commercial-use restrictions for its default [68-point landmark model](https://dlib.net/face_landmark_detection.py.html). The release weight archive's README reports frontal-head training and provides no additional model license. These facts require clarification before redistributing a bundled model; they do not establish that all personal evaluation is prohibited. Replacing dlib with Vision or MediaPipe would not, by itself, resolve the gaze weights' rights or quality limits. No native Core ML conversion or performance result has been validated.

For a concrete external trial, the project's `v1.0.1-alpha` release publishes `GazeAt-Installer.dmg` with SHA-256 `317d8a20163afc7a23003a132fb2414a5f130f7754b65fb2f1de1522fa0c7b4a`. The downloaded installer matched that checksum. A local evaluation copy passed strict deep code-signature verification and Gatekeeper assessment as Notarized Developer ID, signed by Yuli Wang (team 2K82HGJSWY). After the user approved launch and camera access, the app was evaluated locally. Virtual-camera activation and output-quality validation are separate steps. A checksum establishes artifact identity, not model rights or image quality. For an embedded commercial path, Effects SDK still requires a gaze-enabled native package and license from its vendor; the ordinary trial alone does not provide that feature.

## Local trial on November 13, 2026

- GazeAt 1.1 launched successfully and reported capture from the MacBook Air Camera.
- Its bundled backend loaded the eye model and connected its local shared-memory path after about 11 seconds. The configured processing resolution was 1280 × 720; the capture log reported a 1920 × 1080 input frame. These startup observations do not measure correction latency or frame rate.
- The visible preview initially selected the physical camera. That is not evidence that its image was corrected.
- macOS rejected extension management from the evaluation-cache location because the host must reside in `/Applications`. The verified copy was placed at `/Applications/GazeAt Evaluation.app` and its signature and notarization assessment passed again.
- `systemextensionsctl` reports `com.willywangkaa.gazeatcamera.cameraextension` as waiting for user approval. System Settings → General → Login Items & Extensions → By Category → Camera Extensions shows its switch off. Enabling this additional system extension is pending explicit approval.
- No successful corrected-video output, blinking comparison, or receiving-app compatibility result has been established.

## External virtual-camera path

CueLens's camera picker accepts camera devices exposed through AVFoundation and excludes its own virtual output to prevent feedback. If an authorized gaze-correction app exposes a supported virtual camera, the intended path is:

`Physical camera → vendor correction → vendor virtual camera → CueLens preview/effects`

The meeting app can select the vendor camera directly. Relaying additional CueLens effects into a meeting requires the separately signed and activated CueLens Camera extension. Neither path has been validated with a gaze-correction provider on this Mac. CueLens cannot infer that a vendor's correction is enabled merely because its camera is selected, and must not report native correction as active on that basis.

## Quality limits and acceptance

Natural correction has a working range. NVIDIA's published implementation recommends roughly a 20-degree pitch/yaw cone, reduces correction as the eyes move farther away, and disables it for large head rotations or obscured eyes. This is evidence about that implementation, not a measured CueLens limit or a guarantee for other vendors. [NVIDIA working range and occlusion handling](https://developer.nvidia.com/blog/improve-human-connection-in-video-conferences-with-nvidia-maxine-eye-contact/)

Before enabling a future module, compare raw and corrected video while reading near and far from the lens, blinking, turning the head, wearing glasses, and moving in varied light. Verify identity and eyelid preservation, graceful fallback, instant bypass, bounded queues, actual frame rate/latency, and the image received by a separate meeting client. Until those checks pass, keep correction unavailable rather than promise eyes will stay centered at every angle.
