# Eye-contact correction: integration status

Reviewed November 13, 2026. **CueLens includes an experimental native Core ML eye-correction path.** It requires a compatible local model pair, is off by default, and does not correct head pose. Automatic framing still changes only the crop. Natural eye centering while reading has not been validated across people, angles, and lighting.

An acceptable integration needs a working local model, camera-processing SDK, or independently installed virtual-camera provider, appropriate model and distribution rights, and observed correction on this Mac. A toggle, face detector, or geometric pixel shift does not establish that capability. The user authorized a separate local GazeAt trial. That evaluation is described below; no gaze model or vendor binary is bundled with CueLens.

## Native SDK and model verification

A read-only search of the installed MacOSX27.2 SDK's public AVFoundation, Vision, and CoreImage headers and Swift interfaces found no eye-contact or gaze-redirection API. AVFoundation's documented Center Stage behavior changes framing, while Portrait, Studio Light, and Background Replacement address other effects. None is an eye-redirection switch for CueLens.

The GazeAt candidate's FLX implementation traces to the original [gaze_correction project](https://github.com/chihfanhsu/gaze_correction), which includes trained weights and a BSD source license. Its original [DIRL dataset](https://sites.google.com/site/chihfanhsuwebsite/dataset) is marked for noncommercial use, and dlib separately flags commercial-use restrictions for its default [68-point landmark model](https://dlib.net/face_landmark_detection.py.html). The release weight archive's README reports frontal-head training and provides no additional model license. These facts require clarification before redistributing a bundled model; they do not establish that all personal evaluation is prohibited. Replacing dlib with Vision or MediaPipe would not, by itself, resolve the gaze weights' rights or quality limits. A local Core ML conversion has now run successfully on this Mac; the numerical comparisons and limited timing results below do not establish live-video quality or redistribution rights.

For a concrete external trial, the project's `v1.0.1-alpha` release publishes `GazeAt-Installer.dmg` with SHA-256 `317d8a20163afc7a23003a132fb2414a5f130f7754b65fb2f1de1522fa0c7b4a`. The downloaded installer matched that checksum. A local evaluation copy passed strict deep code-signature verification and Gatekeeper assessment as Notarized Developer ID, signed by Yuli Wang (team 2K82HGJSWY). After the user approved launch and camera access, the app was evaluated locally. Virtual-camera activation and output-quality validation are separate steps. A checksum establishes artifact identity, not model rights or image quality. For an embedded commercial path, Effects SDK still requires a gaze-enabled native package and license from its vendor; the ordinary trial alone does not provide that feature.

## Local trial on November 13, 2026

- GazeAt 1.1 launched successfully and reported capture from the MacBook Air Camera.
- Its bundled backend loaded the eye model and connected its local shared-memory path after about 11 seconds. The configured processing resolution was 1280 × 720; the capture log reported a 1920 × 1080 input frame. These startup observations do not measure correction latency or frame rate.
- The visible preview initially selected the physical camera. That is not evidence that its image was corrected.
- macOS rejected extension management from the evaluation-cache location because the host must reside in `/Applications`. The verified copy was placed at `/Applications/GazeAt Evaluation.app` and its signature and notarization assessment passed again.
- After the user approved enabling the virtual camera, System Settings showed the extension on and `systemextensionsctl` reported `com.willywangkaa.gazeatcamera.cameraextension` as activated and enabled.
- With MacBook Air Camera selected as GazeAt input and Start AI Processing enabled, its Camera, AI Runner, and Stream indicators turned green. CueLens selected GazeAt Camera and received visible video. One short preview reported 30 fps, 22 ms CueLens processing, and zero dropped frames; these are downstream CueLens measurements, not gaze-model latency or quality measurements.
- Eye-centering while reading, blink preservation, angle limits, and video received by a meeting participant remain unverified. No native GazeAt API for starting AI processing was found. Opening the external app or selecting its camera does not itself enable its correction.

## External virtual-camera path

CueLens's camera picker accepts camera devices exposed through AVFoundation and excludes its own virtual output to prevent feedback. If an authorized gaze-correction app exposes a supported virtual camera, the intended path is:

`Physical camera → vendor correction → vendor virtual camera → CueLens preview/effects`

The meeting app can select the vendor camera directly. Relaying additional CueLens effects into a meeting requires the separately signed and activated CueLens Camera extension. The vendor-to-CueLens preview connection was observed on this Mac; the outgoing meeting-client path remains unverified. CueLens cannot infer that a vendor's correction is enabled merely because its camera is selected, and must not report native correction as active on that basis.

## Built-in implementation path

A separate app is not an inherent macOS requirement. CueLens now runs its own gaze inference before effects and framing. The public FLX network exposes optical-flow and lighting-weight tensors for each eye. The native processor uses Core ML with CPU execution, Vision face and eye landmarks, and a Swift warp and blend, avoiding a Python runtime. Converted model weights remain separate local assets and are not included in the public application bundle. Native execution, numerical comparisons with the original model, and a static-image processing check establish a working local path; verified distribution rights and live-video quality validation remain outstanding. [Model implementation](https://github.com/WangWilly/gaze-correction-cam/blob/master/tf_models/gaze_corrector_v1/gaze_warp_model.py), [Apple TensorFlow conversion workflow](https://apple.github.io/coremltools/docs-guides/source/tensorflow-1-workflow.html).

## Quality limits and acceptance

Natural correction has a working range. NVIDIA's published implementation recommends roughly a 20-degree pitch/yaw cone, reduces correction as the eyes move farther away, and disables it for large head rotations or obscured eyes. This is evidence about that implementation, not a measured CueLens limit or a guarantee for other vendors. [NVIDIA working range and occlusion handling](https://developer.nvidia.com/blog/improve-human-connection-in-video-conferences-with-nvidia-maxine-eye-contact/)

Before relying on correction in a meeting, compare raw and corrected video while reading near and far from the lens, blinking, turning the head, wearing glasses, and moving in varied light. Verify identity and eyelid preservation, graceful fallback, instant bypass, bounded queues, actual frame rate/latency, and the image received by a separate meeting client. Until those checks pass, keep correction labeled experimental and do not promise eyes will stay centered at every angle.

## Local Core ML conversion experiment

The original learned left/right FLX checkpoint networks were converted locally to Core ML MLProgram and executed by a standalone Swift program on this M4. The fixed inputs are a 48 × 64 BGR eye patch, 12 channels of raw pixel landmark offsets, and two correction angles; outputs are learned flow and lighting weights. Native CPU-only network medians were 1.69 ms and 1.98 ms in one short run. These times exclude landmark detection, compositing, camera capture, and outgoing video.

Eight synthetic input/angle cases were compared against TensorFlow. Two left-eye cases exceeded a strict 1e-4 tensor tolerance; the largest final corrected-patch difference was approximately 0.194 of one 8-bit level. This establishes numerical feasibility, not natural eye-contact quality. Vision revision 3 with the 76-point constellation produced six-point eye outlines on a public-domain NASA sample. The implemented adapter validates their geometry and maps each eye by its image position rather than assuming dlib index equivalence. An end-to-end native processing check on that static sample applied correction to 473 pixels confined to the eye regions, leaving the rest of the frame unchanged. That result verifies the processing path, not natural eye centering in live video.

Conversion environments, fixtures, models, and compiled model assets remain in ignored local build storage. No model weights or GazeAt executable have been committed or bundled into the public CueLens app. Distribution rights and live-user quality validation remain separate requirements.

A subsequent build 11 device trial reported applied native correction on usable live frames from the MacBook Air camera while GazeAt was closed. Brief applied-status samples showed 30 fps with 13–20 ms processing and zero dropped frames. Larger face angles returned to bypass. This confirms live execution; it does not establish consistent, natural eye contact during reading or corrected video reaching a meeting participant. See [the validation log](validation.md).

## Using the experimental native path

In Camera Studio, **Install Local Models…** imports a compatible compiled `FLX-L.mlmodelc` / `FLX-R.mlmodelc` pair from a selected folder into CueLens's own application-support directory. Both networks are checked before replacement. No GazeAt process or Python runtime is used by this camera path. The local development conversion is for evaluation; its model rights have not been established for public redistribution.

Select a physical camera, enable **local eye correction**, and start the camera. **Before and After** compares raw and processed video; **Bypass** restores the original frame. Session Setup's **Start selected camera with session** remembers camera startup. The correction setting persists, but launching CueLens alone does not start capture. End stops CueLens's camera.

The current geometry assumes a laptop lens above the reading area, with a conservative 10 cm vertical offset. It is not an individually measured gaze calibration. Correction bypasses on missing models, ambiguous or closed eyes, large pose changes, unsupported frames, errors, or resource pressure. A successful applied status means the learned warp was used, not that the viewer perceives perfect eye contact. The CueLens virtual-camera extension still requires separate signing and activation before processed frames can be received in meeting apps.
